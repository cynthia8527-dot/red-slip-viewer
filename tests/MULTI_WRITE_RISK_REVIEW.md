# 多步寫入風險盤點

本盤點只描述草稿 PR #3 目前原始碼與獨立測試專案候選驗證；沒有部署主環境。優先級以「可能留下難以察覺或難以復原的半套資料」排序，後續仍採一次只修一個流程。

| 優先級 | 流程 | 目前寫入順序 | 失敗時風險 | 建議的最小下一步 |
|---|---|---|---|---|
| 高 | `board/` 新增／編輯貨件照片 | Storage 上傳 → Edge Function 建立 `shipment_photos`，逐張重複 | 草稿分支已在資料列失敗時清除本次物件，且網路層無回應時以同一路徑重試一次；Edge 先確認物件存在，相同路徑重送回傳原關聯。瀏覽器在重試前關閉仍可能留下孤兒圖片 | 先在測試專案驗證失敗清理與重送；後續再評估跨頁 pending recovery／定期孤兒掃描，不把跨 Storage／DB 流程宣稱為原子交易 |
| 高 | `shipments` 永久刪除 | 草稿已改為資料庫交易建立私有清理工作並刪貨件／照片 → 刪 Storage → 記錄結果 | 關聯刪除失敗整筆回滾；Storage 失敗保留工作並回 202，同一貨件 ID 重送可繼續。尚無背景 worker，若使用者不重送，物件會暫時保留 | T030 SQL 與離線 Edge 已通過，測試 Edge v9 已部署；先補登入整合，再評估定期 worker／保留期限。主環境未變更 |
| 高 | `calculator/` 新增商品 | `products` insert → `vendor_prices` insert → 可選照片上傳 → 更新商品路徑 | 價格失敗會留無價格商品；照片／路徑任一步失敗會留半套或孤兒檔 | 先讓建立商品＋初始價格共用已驗證 RPC；照片另拆成可重試、可清理步驟 |
| 中 | `board/` 新增貨件後上傳照片 | 冪等建立貨件 → 多張照片流程 | 貨件成功、照片失敗時若誤報整筆失敗，使用者可能再按一次 | 已改為保留既有貨件、清空新增表單並明確顯示「貨件已建立、照片未完整」，引導到編輯補傳；Storage 孤兒清理仍列高優先 |
| 中 | `board/` 快速新增商品＋初始價格 | 草稿已改為 request UUID＋fingerprint 的單一 RPC | 資料庫原子；相同內容重送回傳原商品，改內容拒絕。登入 API 尚未實測 | T031 SQL 依序與並發重送、舊 RPC 相容均通過；已把登入案例加入固定指令，待原 Windows 安全憑證環境執行。主環境未變更 |
| 中 | `vendors/` CSV 匯入 | 逐列新增廠商或據點 | 中途錯誤會留下前半批資料，重跑可能再遇重複或造成部分更新 | 先定義「整批全成／可續跑」規格，再做批次 RPC 或逐列 operation key；保留匯入結果報告 |
| 低 | 廠商、據點、叫車地點的一般儲存 | 各自單筆 insert／update | 沒有半套交易，但回應逾時重按仍可能重複；部分表已有組合唯一限制只在測試專案 | 正式 migration 先完成既有唯一限制，再視實際重送頻率補 idempotency |

已採單次資料庫交易的流程：貨件＋新群組 POST、貨件換群組 PATCH、`board/` 快速新增商品＋初始價格。這不代表其後的 Storage 操作也在同一交易中。

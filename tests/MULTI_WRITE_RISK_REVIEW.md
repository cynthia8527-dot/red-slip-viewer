# 多步寫入風險盤點

本盤點只描述草稿 PR #3 目前原始碼與獨立測試專案候選驗證；沒有部署主環境。優先級以「可能留下難以察覺或難以復原的半套資料」排序，後續仍採一次只修一個流程。

| 優先級 | 流程 | 目前寫入順序 | 失敗時風險 | 建議的最小下一步 |
|---|---|---|---|---|
| 高 | `board/` 新增／編輯貨件照片 | Storage 上傳 → Edge Function 建立 `shipment_photos`，逐張重複 | 草稿分支在資料列失敗時清除本次物件；網路層無回應時以同一路徑重試。上傳前把同帳號待辦存於 `sessionStorage`，重開同一分頁補關聯；最近兩分鐘的物件尚未出現時保留待辦。關閉分頁、清除資料或上傳超過兩分鐘仍可能留下孤兒圖片 | T021 新增五項離線待辦案例通過；登入整合與長時間上傳／孤兒掃描仍待測，不把跨 Storage／DB 流程宣稱為原子交易 |
| 高 | `shipments` 永久刪除 | 草稿已改為資料庫交易建立私有清理工作並刪貨件／照片 → 刪 Storage → 記錄結果 | 關聯刪除失敗整筆回滾；Storage 失敗保留工作並回 202，同一貨件 ID 重送可繼續。尚無背景 worker，若使用者不重送，物件會暫時保留 | T030 SQL 與離線 Edge 已通過，測試 Edge v9 已部署；先補登入整合，再評估定期 worker／保留期限。主環境未變更 |
| 高 | `calculator/` 新增商品 | 防重 RPC 建立商品＋價格 → 上傳前記錄分頁待辦 → 可選照片上傳 → `product-photos` Edge Function 關聯 | 商品與價格已是單一交易；同分頁重開可接續照片關聯，確定失敗會清新物件，換圖會清舊物件。清舊圖前重讀商品路徑，若重新指向舊圖就暫緩刪除；但重讀與刪除仍可交錯，無法保證併發一致性。關閉分頁或清除資料也可能留下孤兒檔 | T032 離線交錯測試通過、測試 Function v3 已部署；先補已登入整合，再設計資料庫協調／持久工作與孤兒掃描 |
| 中 | `board/` 新增貨件後上傳照片 | 冪等建立貨件 → 多張照片流程 | 貨件成功、照片失敗時若誤報整筆失敗，使用者可能再按一次 | 已改為保留既有貨件、清空新增表單並明確顯示「貨件已建立、照片未完整」，引導到編輯補傳；Storage 孤兒清理仍列高優先 |
| 中 | `board/` 快速新增商品＋初始價格 | 草稿已改為 request UUID＋fingerprint 的單一 RPC | 資料庫原子；相同內容重送回傳原商品，改內容拒絕。登入 API 尚未實測 | T031 SQL 依序與並發重送、舊 RPC 相容均通過；已把登入案例加入固定指令，待原 Windows 安全憑證環境執行。主環境未變更 |
| 中 | `vendors/` 舊通訊錄 Excel 匯入 | 逐列新增廠商或據點 | 中途錯誤會留下已寫入的前半批；若回應遺失，當筆是否已入庫未知，重跑可能遇到重複。草稿網頁現明示已確認成功的筆數及不確定性，嘗試重新讀取後提醒核對 | 尚未提供整批原子性或可續跑保證；先以測試專案資料定義「整批全成／可續跑」規格，再評估批次 RPC 或逐列 operation key 及匯入結果報告 |
| 低 | 廠商、據點、叫車地點的一般儲存 | 各自單筆 insert／update | 沒有半套交易，但回應逾時重按仍可能重複；部分表已有組合唯一限制只在測試專案 | 正式 migration 先完成既有唯一限制，再視實際重送頻率補 idempotency |

已採單次資料庫交易的流程：貨件＋新群組 POST、貨件換群組 PATCH，以及 `board/`／`calculator/` 的新增商品＋初始價格。這不代表其後的 Storage 操作也在同一交易中。

T032 剩餘併發情境：請求 A 換成新圖並查到舊圖已不再使用；在 A 呼叫 Storage 刪除前，另一個請求 B 又把舊圖設回商品，A 仍會刪到目前使用中的圖片。單純增加一次讀取無法消除這個讀取／刪除時間窗。後續需要以資料庫交易確定「可清理」狀態並禁止重新關聯待刪路徑，或改成持久清理工作與明確的路徑世代規則；在測試專案用兩個請求及可控 Storage 延遲重現 A／B 交錯、驗證最後商品路徑仍有物件，再考慮正式 migration。測試 SQL 不得直接套入主環境。

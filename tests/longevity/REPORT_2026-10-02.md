## 問題與最短還原

1. **L002 高（新）：刪除後重送使貨件復活。** 建立 K → 作廢 → 永久刪除 →
   原 body＋K 延遲重送；201、replayed=false、全新 ID。不是兩筆同時存活，但舊请求可重新建貨件。
   下一步先定義 request ID 保留／過期規則，再設計刪除後仍可辨識的防重紀錄。
2. **L004 高（既知）：並發換圖會刪到目前使用的圖。** A 換新圖 N，最後重讀後暫停；
   B 換回舊圖 O 並刪 N；A 接續刪 O。兩請求 201，DB 最後仍指 O，但 Storage 替身沒有 O。
   需跨請求協調／路徑世代或持久清理設計，單加一次重讀不夠。
3. **L003 中（新）：跨月／跨年凌晨貨件落錯月份。** 台北 2028-01-01 00:00
   的原始時間為 `2027-12-31T16:00:00+00:00`；實際月份篩選不把它列入 2028 年 1 月。
   下一步可做窄修：統一台北年月轉換及對應 UI 回歸。
4. **L001 中（新）：金額保存二進位浮點尾數。** 單價 0.10，3 kg，一次已出貨 POST：
   DB 寫入 `0.30000000000000004`；SQL `= 0.30` 為 false。
   升級後 70×12.345 的新金額也未精確等於 864.15。未證明畫面有可見的分位錯帳；
   先定義金額小數位／捨入規則，再決定十進位計算落點，不能任意四捨五入掩蓋。

最短案例在 `risks.test.mjs`，是真正紅燈，不是把已知錯誤當預期而標 PASS。
一般序列異常會輸出 seed、第一個失敗步驟與完整 prefix；可選 reducer 有次數上限，
只有完成才宣稱 deletion-minimal，未宣稱數學上的全域最短。

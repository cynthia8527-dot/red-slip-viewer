# 每筆整元修正與年度情境結果

使用者於 2026-10-02 明確選擇「不要保留，就單筆整數好了，合計再算容易跑歪」。
本修正從草稿 PR #3 的 `c739d8c0e7a35c6c1ab7fdc1b77968e119451f90` 接續，
只修改候選程式及合成測試；沒有修改 Drive 帳本、正式 DB、正式 history 或部署。
金額規則是這次明確選擇，不宣稱所有歷史帳本一直使用同一政策。

## 實際程式變更

- `shipments` Edge 新快照：十進位拆成 BigInt 分子／分母，先精確相乘，沿用最低計價
  下限，再將單筆結果四捨五入到整元；正負半值皆離零。
- 不改重量／單價欄位、可輸入精度、DB migration、既有最低計價語義或非 kg 計價範圍。
  例 `0.29 × 50` 應為 15，不能因 binary float 的 `14.499999999999998` 而成為 14。
  `70 × 12.345` 新快照是 864；單價仍是 70、重量仍是 12.345。
- 同請求重試、已出貨再次 PATCH、備註、作廢／恢復維持凍結值；既有歷史小數金額不回填。
  既有功能若明確將已出貨退回待出貨再重新出貨，原本就會清除／重取快照；屆時新快照採新規則。
- 超過 JS safe integer 的整元結果以數字字串送入 SQL numeric，避免寫入時再次轉壞。
  **未改**既有 PostgREST JSON／前端 Number 的超大數字讀取與顯示限制，不能宣稱全系統任意精度。
  計算精確性以原有輸入管線交給計價函式的十進位值為界，不擴大輸入驗證或重設資料型別。
- 原產品沒有月帳人工調整／稅額／開票 endpoint。本輪沒有擴建這些功能；匿名規則測試
  驗證可重用的進位原語與計算順序，不能宣稱已完成月帳引擎或實帳核帳。

## 規則與匿名案例

單筆先 ROUND(qty × price,0)；存在人工調整時再 ROUND(該整元金額 + adjustment,0)，
之後才加總。開票稅為 ROUND(整元未稅合計 × 0.05,0)，不開票為 0，總額=未稅+稅。
不把原始金額直接乘 1.05，也不把顯示兩位小數當作會計精度。

| 匿名案例 | 結果 |
|---|---|
| 10.5 × 15、20.5 × 15 | 158、308；未稅466、稅23、總額489 |
| 同兩筆但不開票 | 未稅466、稅0、總額466 |
| 158 加人工調整 -0.5 / +0.5 | 158 / 159 |
| -158 加人工調整 -0.5 | -159 |
| 未稅10 / -10 的5%稅 | 1 / -1（負半數純合成） |
| 0.10 × 3 | 新快照0，不再儲存0.30000000000000004 |
| 舊快照864.15、後续編輯備註 | 仍為864.15 |
